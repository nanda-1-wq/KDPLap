## 3 · The causes, weighed

### H4 · A stale or cached link: **ruled out**
The pick path, step by step:
1. The browser sends only `{ action, source, id, bookId }`. Any other key is refused (`lib.ts:140-147`), so no URL can come from the browser.
2. `pickPixabay` looks the picture up by id at Pixabay on every pick (`handler.ts:188-189`, comment: "never a URL from the browser or the cache"). `pixabayLookupUrl` is `?key=…&id=…` (`lib.ts:180-182`).
3. `largeImageURL` is read from **that** answer (`handler.ts:192` → `lib.ts:265`), microseconds after it arrives.
4. The download starts right away (`handler.ts:196`).
5. `stock_cache` is read only by `search` (`handler.ts:150`). The pick never reads it. There is no other cached lookup.

The log agrees. At 10:00:56 a second, full pick did a new lookup (200) and still got 429 on the download. A dead link would also more likely answer 403, 404 or 410 than 429.
**So the fresh lookup is already there.** Nothing to change.

Side note (the browser, not the 429): tiles and previews show links from search answers that may come from `stock_cache`, up to 24 h old (`lib.ts:21`, `handler.ts:150-155`; `checkCached` checks hosts, not age, `lib.ts:340-356`). Pixabay says `webformatURL` is "URL valid for 24 hours". So a tile from a nearly 24 h old answer may not load. This is rare and it does not cause the 429. Option: `CACHE_MS` 23 h. My recommendation: leave it out of E16.2 and add a roadmap line (N3).

### H1 · Browser `/get/` loads on our key: **weak**
| Failed pick | Key-bound loads in the browser before it | Last load before the pick |
|---|---|---|
| A3 08:03:41 | **6 tiles** (`webformatURL`). At 70344c7 the panel showed 6 (shot `a3-02-pixabay-busy.png`). **0 large previews**: the pick came from the panel, the large view was closed | about 17 s |
| E3 13:09:23 | up to 70 tiles over 3 pages. They load lazily, so only tiles scrolled into view. No preview recorded | about 90 s (page 3 at 13:07:51) |
| 10:00:41 | no search in 28 min. At most 1 preview (a PREVIEW click loads `largeImageURL`, `stock.js:376`) or tiles scrolled into view | unknown |

Against H1:
- The **lookup in the same pick passed** every time. Pixabay's documented limit is 100 requests per 60 s **per API key**, and we sent at most 4 a minute. So the API's own per-key budget was not used up. H1 would need a separate, much smaller `/get/` budget that 6 tiles can use up.
- Pixabay expects search tiles to load in browsers: "Returned image URLs may be used for temporarily displaying search results."
- The two retries that worked came after periods with no new tile loads, but so did 2 of the 3 failures.

The plan's front-end options:
- **c) lazy tiles is already in the code**: `loading="lazy"` on every tile (`stock.js:300`).
- **a) a preview that reuses the thumbnail** would save at most 1 load per PREVIEW click. Under H5 it would even make things worse (see below).
- **b) `previewURL` tiles** (150 px) would make every tile soft, to fix a cause the records do not support.

**Recommendation: no front-end change for H1** (D2).

### H2 · A limit per outbound IP: **possible, cannot be tested from the code**
- Pixabay's docs say API requests are counted "with the API key, and not with your IP address". That is about `/api/` only. `/get/` (the file links) has no documented limit.
- Edge Functions share outbound addresses with other projects. Another project's traffic could trip a per-IP rule on `/get/` at random times. That fits failures with no pattern on our side.
- The only remedy is the retry and the countdown.

### H3 · A filter on the User-Agent: **possible, cheapest to fix**
- `getJson` passes `{}` as headers for both Pixabay calls (`handler.ts:162`, `:189`). `download()` passes no headers at all (`handler.ts:117`). So the runtime's defaults go out: a `Deno/…` User-Agent (§4) and `Accept: */*`.
- The lookup (`pixabay.com/api/`) passes with the same User-Agent and the same host. So if a filter exists, it is on the file path, which is what a bot shield for images would guard.
- Each 429 came back fast. At 08:03:41 the row, the lookup and the download 429 all fall in the same second. That fits an edge shield answering before the file server.
- The fix costs one header line. It has no visual effect and can be undone.

### H5 (new) · The 1,280 px file is made on its first request: **possible**
- In every failure with records, the server's download was, as far as we know, the **first request ever** for that picture's large file. In A3 the large view was closed, so the browser never loaded `largeImageURL`.
- The tries that worked were later tries for the same picture, 84 s and 231 s on. A try 15 s on failed (10:00:56).
- This is not documented by Pixabay. It is a pattern that fits, nothing more.
- **Test in Part 4 (no extra code):** pick one picture right after opening its PREVIEW (the browser loads its large file first, `stock.js:376`), and pick another straight from a tile. That adds 1 lookup and 1 download to Part 4's budget (5 or 6 Pixabay requests, not 4). It needs your OK.
- If H5 holds, no server change can make the file appear sooner. The countdown is the fix.

### The fix at the cause I propose
1. **D1, H3:** every Pixabay request from stock (the search, the lookup and every download hop) sends:
   - `User-Agent: NicheInk-stock/2 (+https://nicheink.com)`, with no personal data;
   - `Accept: application/json` on the API, and `Accept: image/jpeg, image/png` on the file.
2. **D3, so Part 4 can tell H2, H3 and H5 apart:** the 429 log line adds the hop (0 to 3) and the host (`pixabay.com` or `cdn.pixabay.com`, never a path or query). Today the line is written after the redirect loop (`handler.ts:131-132`), so we cannot tell which hop answered. It also adds the body's type (`html`, `text`, `json` or `other`, from Content-Type, never the body). An HTML 429 points to an edge shield (H2 or H3). A text 429 points to Pixabay's own server. Example:
   `stock: pixabay download HTTP 429 (try 1 of 2, hop 0 pixabay.com, body html, wait 0 s, retry-after -, reset -, remaining -)`.
3. **D2:** no front-end change for H1.
4. The retry and countdown stay as the fallback for H2 and H5 (§5).
5. **D6:** the server retries only the step that failed. A download 429 retries the download with the same link (it is seconds old). It does not do a new lookup, so it costs no extra API call. A lookup 429 retries the lookup.

### 5.3 How to decide: one read-only row check (Claude chat)
A successful pick leaves a `cover_assets` row. A fresh search leaves a `stock_cache` row (`fetched_at` is the server clock, `0031:103`). The SQL counts rows only and reads no content. It includes 3 known controls to show the method works. It reads the owner's rows as counts, so it needs **the owner's OK**.

```sql
-- E16.2 STOP 0: what each POST 200 made (Nov 18 UTC). Read only, counts only.
-- A found row proves the kind. No row proves nothing (a picture can be removed with ×,
-- and a cache row is overwritten by the same search or purged after 24 h).
select w.label, w.t,
  (select count(*) from public.cover_assets a
    where a.source = 'pixabay' and a.created_at between w.t - interval '2 seconds' and w.t + interval '15 seconds') as pixabay_picks,
  (select count(*) from public.cover_assets a
    where a.source = 'unsplash' and a.created_at between w.t - interval '2 seconds' and w.t + interval '15 seconds') as unsplash_picks,
  (select count(*) from public.stock_cache c
    where c.fetched_at between w.t - interval '2 seconds' and w.t + interval '15 seconds') as fresh_searches
from (values
  ('control: A3 Unsplash pick (expect 1 unsplash)', timestamptz '2026-11-18 08:02:29+00'),
  ('control: A3 Pixabay retry (expect 1 pixabay)',  timestamptz '2026-11-18 08:07:33+00'),
  ('control: E3 Pixabay retry (expect 1 pixabay)',  timestamptz '2026-11-18 13:10:48+00'),
  ('owner 09:27:25', timestamptz '2026-11-18 09:27:25+00'),
  ('owner 09:27:34', timestamptz '2026-11-18 09:27:34+00'),
  ('owner 09:32:02', timestamptz '2026-11-18 09:32:02+00'),
  ('10:00:59 after two 429s', timestamptz '2026-11-18 10:00:59+00')
) as w(label, t)
order by w.t;
```
If the log shows each request's run time, that helps too. A Pixabay pick (lookup, download, upload, row) runs for seconds. A cache-hit search runs for well under 1 s.

**The rule (D4):**
- 10:00:59 **is** a Pixabay pick → failures are per request, not a window. A quick retry can work. Use **2 retries within 20 s**.
- 10:00:59 **is not** a Pixabay pick, or the check cannot tell → keep **1 retry within 5 s** (the plan). For a 429 with no header, I would even skip the blind server retry and go straight to the countdown. That saves one `/get/` request while we may be limited. Your call (D4b).

### 5.4 The countdown with no header: **20 s** (replaces 65 s, Q-9)
- The panel counts down 20 s, retries once on its own, then shows design 63's "Try again in a minute" message.
- Only the unproven 10:00:59 supports 20 s. The proven floor is 84 s, so the design 63 message after the automatic retry covers the longer case.
- Part 4 replaces 20 s with the header numbers it sees.
