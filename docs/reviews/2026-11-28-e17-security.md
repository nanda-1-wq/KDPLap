## Findings

### L1 (low). save_part_version takes p_make_current from the browser, and versions have no count cap
- supabase/migrations/0035_book_parts.sql:653-704 (granted to authenticated at :1870).
- With `p_make_current = false`, the function skips the base check (:677-689) and inserts a new manual version.
  Only copy_bio_to_about (:802) needs this path. A signed-in user can call it in a loop and add rows of up to
  20,000 characters to their own part. Nothing caps the versions per part.
- Why it matters: it cannot touch another user's data (part_lock reads through RLS, and the guard checks the owner).
  The only risk is one user filling the database. Sections have the same shape today (js/supabase.js:896, 0018).
  The risk grows in v3, when other users come in.
- Fix proposal (v3, with the other multi-user limits): a per-part version cap or a rate limit inside the RPC, set as a
  constant (rule Nov 20: no limit inputs). Or move the "not current" insert into copy_bio_to_about and drop the
  parameter from the granted function. Do the same for sections.

### L2 (low). The guards trust session flags (transaction-local settings)
- 0035:306, :320, :350-353, :448, :494 read `kdp.part_write`, `kdp.part_suggestion_apply`, `kdp.part_suggestion_use`
  and `kdp.also_by_write`. The RPCs set them with `set_config(…, true)` and clear them (:692/:700, :746/:753,
  :811/:817, :919-934, :1061/:1104).
- Why it matters: the guards hold only while no browser can set these flags. Today they cannot. PostgREST callers
  cannot run `SET`, `pg_catalog.set_config` is not in an exposed schema, and every `set_config` in
  `supabase/migrations/*.sql` uses a fixed `kdp.*` name with `'on'` or `''`. I grepped for any other form and found
  none. The same pattern is used for sections (0018, 0021).
- Fix proposal: no change now. Add a small test that fails when a migration calls `set_config` with a name that is
  not a fixed string, so a later RPC cannot open this by mistake.

### L3 (low). apply_part_suggestion's text match can be slow in the worst case
- 0035:898-910. Each pass of the loop copies `substr(p_full_text, v_from)`. With a 1-character output repeated many
  times, the work grows with the square of the text length (at most about 45,000 characters).
- Why it matters: the length check (:898) runs first, the output comes from the AI and not from the browser, and the
  statement timeout ends a slow call. The loop is copied from 0021 (section_suggestions).
- Fix proposal: none needed before the merge. Later, for sections and parts together: use `strpos` with a start
  position (no copy), or compare at the one place the browser says the passage is.

### L4 (low). confirmDialog has a raw HTML option
- js/book-write.js:897 (`html` parameter), :924 (`innerHTML = html`). It has one caller today, :529, which escapes
  the pen name with `esc()` before it is bolded.
- Why it matters: it is safe today. But a future caller that passes unescaped text gets an XSS sink in a shared
  dialog.
- Fix proposal: build the bold pen name as DOM nodes (a `<strong>` with `textContent`) and remove `html`. Or keep
  `html` and add a test that the 80b dialog shows a hostile pen name as text.
