## 1. P2: measure first

**What I found.** On each keystroke, `onInput` (`js/book-write.js:1565`) runs `MD.fromDom` on the whole editor, `imp.onInput()`, `chk.onInput()` (already debounced, 400 ms), `renderWords` (word count), `renderFoot`, `renderManuscriptCount` (word count through `sectionWords`) and, **only when the Versions tab is open**, `renderSide()`. That rebuilds the whole panel and calls `chk.count()`, which runs `T.check` on the full text (memoized, but the text changes every keystroke), plus a third word count in the "Unsaved changes" row. When the Checks tab is open, `renderSide` is skipped and the checks wait for the 400 ms debounce.

**Timing check (new test):** `tests/browser/write/t-timing.js`, run with `tests/browser/run.sh write t-timing.js`.
- It uses the write mock and replaces section W7 1.1 (`st.long`) with a generated text of at least 16,000 words and under 99,000 characters. The test asserts both numbers, so the section never hits the 100,000 limit.
- An init script wraps `addEventListener` so that every `input` listener on `[data-editor]` is timed. The listener times of one event are added up, which gives the time spent in the input path for each keystroke.
- It clicks the end of a middle paragraph and types 50 characters with `keyboard.type` (60 ms delay, so the 400 ms debounce does not fire mid-burst). It runs once with the Versions tab open and once with the Checks tab open.
- It reports the median and the worst time for each tab. It also reports, separately, the time of the debounced check refresh after typing stops and any long tasks over 50 ms. Event Timing (keystroke to next paint) is listed for information.
- PASS lines (fixed count): the section size, all 50 characters arrived in the editor, the draft was sent, the median is 16 ms or less. The numbers print as `INFO` lines. Note: a timing assertion can flake on a busy machine. If it does, I will tell you rather than loosen it quietly.

**Decision rule (yours):**
- If the median with Versions open is 16 ms or less: P2 code stays as is, the test is kept, and I report the numbers.
- If it is over 16 ms, I apply the G1 fix (S size):
  - Count the words once per input. A small cache `curWords()` (last text → count) is used by `renderWords`, `sectionWords` (for the open section) and the "Unsaved changes" row. Same numbers.
  - With Versions open, typing calls a new `renderUnsavedRow()` instead of `renderSide()`. It updates only the word count in the "Unsaved changes" row. When the row has to appear or go (the first keystroke, or typing back to the saved text) or there is no list yet, it falls back to the full `renderSide()`, so the markup stays exactly the same.
  - The tab count comes from the debounced `chk.refresh()`, which `chk.onInput()` already schedules.
  - Then I measure again and report before and after.

**Proof of no change:** the write suite stays at 479 (t-versions and t-checks cover the row and the tab count). New behaviour to note: with Versions open, the Checks count updates 400 ms after typing stops instead of on every keystroke. This is the change G1 proposed and you listed. If an existing test needs editing because of it, I stop and report.

**Risk:** low to medium. The row patch must produce the same HTML as `versionsHtml()`. I will compare the panel's `innerHTML` after the patch with a fresh `renderSide()` in the new test (one PASS line).

```js
// Not on window.kdp: the three calls below share the session read, URL and headers.
async function postGenerate(input, { signal, onSent } = {}) → { res } | { fail: 'unauthorized' | 'aborted' | 'network' }
```
