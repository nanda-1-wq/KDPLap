## 2 · What stock v2 does

### 2.1 The limits (0032), before any provider call
- **Search:** read the cache first, then `rpc stock_reserve(p_source, p_action: "search", p_provider_calls: 0 for a cache hit, else 1)`.
- **Pick:** `stock_reserve(source, "pick", 1 for Pixabay, 2 for Unsplash)`, then the provider.
- `p_provider_calls` goes as a JSON number (PostgREST types it as `smallint` from the signature; Part 4 proves it).
- The answer is checked (`L.parseReserve`): `{ok: true, id}` with a positive whole id, or `{ok: false, code: rate_limited | stock_busy}`. Anything else → 500 `server_error`, with no provider call (log: `stock: reserve answer not understood`).
- An rpc error → 500, with no provider call (fail closed, as today).
- A refusal → 429 `rate_limited` or 503 `stock_busy` (no `retry_after_s`: that is only for a busy Pixabay pick).
- `stock_usage()` and the direct `stock_calls` insert are **no longer used** by stock v2 (B2, §7).
- `STOCK_UNSPLASH_HOURLY` is **no longer read**. The secret can be removed after the deploy. `SEARCHES_PER_MINUTE`, `PICKS_PER_MINUTE`, `UNSPLASH_HOURLY_DEFAULT` and `unsplashBudget` are gone from `lib.ts`: the numbers live only in 0032 (one source of truth).

### 2.2 Release
After a reserved request fails with `stock_busy`, `stock_unavailable` or `server_error` (also an unexpected error), the function calls `rpc stock_release(p_id)`.
- Never after: success, `too_large`, `bad_image`, `not_found`, `not_configured`, a refusal, or a cache hit.
- A release that fails or is refused never changes the reply. Log: `stock: release failed: <code>` or `stock: release refused`.
- It covers searches and both sources. 0032 still counts Unsplash calls toward the budget after a release.

### 2.3 The Pixabay pick retry (STOP 1 inputs)
| Rule | Value |
|---|---|
| Retries | **at most 2 for the whole pick**, shared by the lookup and the download (see Q3) |
| Waiting | **at most 20 s in all** |
| Deadline | **45 s** for the whole pick, from after the reserve. Each try's timeout is cut to the time left (lookup 10 s, download 20 s at most). No try starts with under 2 s left |
| Retried | HTTP 429, 502, 503, 504, and a network error (`TypeError`) |
| Not retried | a timeout, any other 4xx, a refused redirect, a file too large, a file that is not a JPEG or PNG |
| Which step | **only the step that failed (D6).** A download retry starts again at the same first link (seconds old), with no new lookup; a lookup retry repeats the lookup |
| Wait with a header | `Retry-After` in seconds, else `Retry-After` as an HTTP-date (IMF-fixdate only), else `X-RateLimit-Reset`. At least 1 s |
| Wait with no header | retry 1: 1.5 s + jitter up to 1 s; retry 2: 4 s + jitter up to 2 s (at most 8.5 s together) |
| A wait is taken only if | a retry is left, the wait keeps the total within 20 s, and the wait plus 2 s still fits before the deadline |
| Out of retries, 429 | 503 `stock_busy` with **`retry_after_s`**: the header rounded up (1 to 120), or **20** with no header |
| Out of retries, 502/503/504/network | today's code: 502 `stock_unavailable`, no `retry_after_s` |

D4b is not used: a 429 with no header gets the quick retries.
Searches and Unsplash are never retried (Q-8).
Worst case for one pick: about 45 s. That is within the Free plan's 150 s wall clock, and `functions.invoke` sets no timeout (STOP 0 §8).

### 2.4 User-Agent and Accept (D1)
Every Pixabay request (the search, the lookup, each download hop of each try) sends:
- `User-Agent: NicheInk-stock/2 (+https://nicheink.com)`;
- `Accept: application/json` for the API, and `Accept: image/jpeg, image/png` for the file.

Unsplash requests are unchanged (tested: they carry no NicheInk User-Agent).

### 2.5 The log line (D3)
One line per failed try of a pick step. It contains numbers, the host name, short types and short header values only:
```
stock: pixabay download HTTP 429 (try 1 of 3, hop 1 cdn.pixabay.com, server cloudflare, cf-mitigated challenge, type html, bytes 20, wait 2 s, retry-after -, reset -, remaining -)
stock: pixabay download failed: TypeError (try 1 of 3, hop 0 pixabay.com, wait 2 s)
stock: pixabay download deadline reached
```
- `try N of M`: M = this try + the retries still left for the pick.
- `hop`: the redirect hop that answered (0 to 3). Host only, never a path or query.
- `server`, `cf-mitigated`, `reset`, `remaining`: header values cut to 40 characters of `[A-Za-z0-9 ._/-]`, `-` when absent. So no `:`, `?`, `=` or `&` can reach the log.
- `type`: `html`, `json`, `text`, `other` or `-`, from Content-Type.
- `bytes`: Content-Length, else the body counted up to 64 KB (`>65536` past that). The body is dropped and never logged.
- `wait`: the wait before the next try, to 0.1 s (`0 s` = no more tries).
- `retry-after`: the header's wait in seconds (rounded up), or `-`.
- Other failures keep today's short lines (`stock: pixabay download HTTP 403`, `… failed: TimeoutError`, …).
- **Added (not in the plan):** every log line passes a last filter that replaces either source key with `[key]`. A provider that echoes our key in a header still cannot get it into a log (tested).

### 10.2 What changed in 0032
**`stock_calls_guard()`** (the insert trigger on `stock_calls`):
1. As before: `at := now()`, `released_at := null`.
2. **New:** a signed-in caller whose row names another user is refused first: `42501 stock_calls: own rows only`. RLS refused that row anyway (after the trigger). Now it stops before any count, so the error can never tell B that A is at the cap.
3. **New:** for an Unsplash row with calls > 0, it takes the per-user lock (`'nicheink.stock.user:' || user_id`), then the shared lock (`'nicheink.stock.unsplash'`). Same keys and order as `stock_reserve`, so no circle wait. Inside `stock_reserve` both are already held, and taking them again is free.
4. **New:** the user's Unsplash calls in the hour (released rows counted) + this row > 30 → `P0001 stock_busy`, detail `Unsplash: 30 calls an hour per user.`
5. **New:** all users' Unsplash calls in the hour + this row > 45 → `P0001 stock_busy`, detail `Unsplash: 45 calls an hour for all users.`
6. Cache hits (0 calls) and Pixabay rows: no lock and no count, as before.

`stock_reserve`, `stock_release`, My layouts: **unchanged**. The header and the table comment say what the guard now does. One change stock v1 can see: at the cap its insert fails, and v1 answers 500 (it cannot log the call, so it fails closed). With one user and v1's own check at 45, v1 only reaches this at 30 Unsplash calls in an hour.

### 10.3 Why the guard is a security definer, and how it stays safe
The per-user count works as invoker (RLS shows a direct insert its own rows). **The shared 45 does not:** under RLS the invoker sees only its own rows, so the all-users sum would just be the user's own sum. The mutation "invoker" in §10.4 shows this: 8 checks fail.

I made **the guard itself** the definer, not a separate definer helper. A helper called from an invoker trigger must be executable by `authenticated`. Then any user could call it by hand and read how many Unsplash calls all users made this hour. A trigger function has no such surface. It stays safe because:
- **It cannot be called on its own.** Postgres refuses a direct call of a trigger function (`0A000`, tested as the owner). `execute` is revoked from public, anon and authenticated (tested).
- **No inputs** but the new row. No limit or budget comes in from outside: 30 and 45 are constants (B1). t0032 checks that the guard and `stock_reserve` carry the same 2 constants.
- **`search_path = ''`**, every name schema-qualified (tested).
- **It only checks and refuses.** It writes nothing but `at` and `released_at` on the new row. The purge stays its own definer trigger, as in 0031.
- **Another user's row is refused before any count** (point 2 above), so a definer count never leaks through an error.
- **Owner:** the §5.2 run-after-apply query in STOP 1 should now list `stock_calls_guard` with `stock_reserve` and `stock_release` (function owner = table owner, postgres). Otherwise the guard would sit under RLS and the shared sum would count only the caller's rows.

Two older checks changed to match: t0031 "only `stock_calls_purge` is a definer" now expects `stock_calls_guard` too (marked 0032), and t0032 "both guards still invoker" is split (My layouts guard: invoker; stock guard: definer, no arguments, empty search_path, trigger only).
