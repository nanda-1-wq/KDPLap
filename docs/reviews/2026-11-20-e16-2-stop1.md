## 3 · What 0032 does

### 3.1 `stock_calls.released_at`
- New column, `timestamptz`, null = counted.
- `stock_calls_guard` now also sets `released_at := null` on insert. So no one can insert a released row. stock v1 never writes it.
- Partial index `stock_calls_unsplash_at_idx on stock_calls (at) where source = 'unsplash'`, for the shared sum.

### 3.2 `stock_reserve(p_source text, p_action text, p_provider_calls smallint) returns jsonb`
Security definer, volatile, `search_path = ''`, every name schema-qualified. **Exactly 3 arguments, none for a limit (B1).**

| Constant | Value |
|---|---|
| searches per user per minute | 30 |
| picks per user per minute | 10 |
| Unsplash calls per hour, all users together | 45 |
| Unsplash calls per hour, per user | 30 (STOP 1 decides, §6) |

Steps:
1. `auth.uid()` null → 42501 "stock_reserve: sign in first".
2. Input check → 22023 "stock_reserve: bad input". Allowed: a search with 0 or 1 call; a Pixabay pick with 1; an Unsplash pick with 2. (Stricter than the plan's "0 to 2": each action and source has its one count.)
3. `pg_advisory_xact_lock(hashtextextended('nicheink.stock.user:' || uid, 0))`.
4. Unsplash with calls > 0: also the shared lock `'nicheink.stock.unsplash'`. The user lock always comes first, so no deadlock.
5. The minute count (this action, this user, released rows excluded) at 30 or 10 → `{ok: false, code: 'rate_limited'}`.
6. Unsplash with calls > 0 (released rows included):
   - the user's own sum + this call > 30 → `{ok: false, code: 'stock_busy'}`;
   - the sum over all users + this call > 45 → `{ok: false, code: 'stock_busy'}`.
7. Insert the row with `user_id = uid` → `{ok: true, id}`.

The answer carries only `ok`, `code` or `id`. No counts of other users.
An Unsplash cache hit (0 calls) takes no shared lock and is never refused by the budget, as in v1.

### 3.3 `stock_release(p_id bigint) returns boolean`
Security definer, volatile, `search_path = ''`. Takes the same per-user lock, then sets `released_at = now()` only when:
- the row is the caller's own;
- it is not released yet;
- it is younger than 2 minutes;
- the caller has fewer than 5 releases in the last hour.

Null or unknown id → false. Signed out → 42501.

### 3.4 Grants
For both functions: `revoke execute … from public, anon` and `grant execute … to authenticated`.
The guard functions stay revoked from everyone.

### 3.5 My layouts
- `drop constraint cover_my_layouts_book_key` (the one-per-book unique key).
- New index `cover_my_layouts_book_order_idx (user_id, from_book_id, exported_at desc, id desc)`.
- `cover_my_layouts_guard` INSERT branch (stays **invoker**):
  1. `pg_advisory_xact_lock(hashtextextended('nicheink.my_layouts:' || new.user_id, 0))`;
  2. 100 entries and this book has fewer than 5 → `my_layouts_full`, as today;
  3. delete this user's entries **of this book** past the newest 4 (`order by exported_at desc, id desc`), so the new one makes 5.
- Never touched: other books, null-book entries, `cover_assets`, Storage (B5).
- The UPDATE branch is 0030's, unchanged (copied word for word).

### 3.6 Unchanged for stock v1
`stock_usage()`, the direct insert policy on `stock_calls`, RLS on `stock_calls` and `stock_cache`, no update or delete for authenticated. v1's rows count for `stock_reserve`, and v2's rows count for `stock_usage` (both tested).

## 5 · Points for Claude chat's review

1. **`smallint` and PostgREST.** In plain SQL, `stock_reserve('pixabay','pick',1)` does not resolve (42883), because `1` is an integer. The tests pass `1::smallint`. PostgREST types RPC arguments from the function's own signature, so `supabase.rpc('stock_reserve', { p_source, p_action, p_provider_calls: 1 })` should work. The Part 2 Deno tests use a fake store, so they cannot prove it. **Part 4's live check proves it** (and the stock v2 smoke after deploy). I kept `smallint` because the plan says so. Switching to `int` is a one-word change if you prefer.
2. **Run after apply (read only):** the definers must be owned by the role that owns `stock_calls`. Otherwise RLS would apply inside them, and the shared sum would count only the caller's rows.
   ```sql
   select p.proname, p.proowner::regrole as fn_owner, c.relowner::regrole as table_owner
     from pg_proc p, pg_class c
    where p.pronamespace = 'public'::regnamespace and p.proname in ('stock_reserve', 'stock_release')
      and c.oid = 'public.stock_calls'::regclass;
   -- expect fn_owner = table_owner (postgres) on both rows
   ```
3. **The input check is stricter than the plan** (each action and source has its one call count). An unknown combination is a bug in the function, so it raises 22023 and stock v2 answers 500 (fail closed).
4. **The My layouts lock key uses `new.user_id`.** B inserting with A's user id takes A's lock for that one statement, which then fails (42501). That costs milliseconds. B cannot hold a transaction open through PostgREST. Nothing else is reachable: the trim runs under B's RLS and deletes nothing of A's (tested, and in rls_cross_user).
5. **Time windows use `now()`** (the transaction's start), as `stock_usage` and the guard do. A request that waits on the lock still counts rows committed by the request before it, because each statement in a volatile plpgsql function takes a new snapshot (the race proof shows it).
6. **The trim inside a bulk insert** sees the earlier rows of the same statement (tested: 3 in one statement still end with 5). The front end only ever inserts one.
7. **`stock_usage()` still counts released rows.** That is v1's reading, unchanged by plan. After a rollback to v1, a released row counts again, which is stricter. Never looser.
8. **B2 stays open** (in the migration header too): after stock v2 is live and checked, drop the direct insert policy on `stock_calls` and `stock_usage()`, in 0033 or its own migration, on the owner's word.
