## Findings already read from the code (Part 0 confirms them and adds the log facts)

### F1 · What one Pixabay pick does (`supabase/functions/stock/handler.ts:186`, pickPixabay)
**Before any provider call:**
- `store.usage()` reads `stock_usage()` (`handler.ts:251`).
- Then `logCall` inserts the `stock_calls` row (`handler.ts:187`).

**Request 1, the lookup:**
- `https://pixabay.com/api/?key=…&id=<id>` (`lib.ts:180`), with a 10 s timeout.
- This is the API. Its documented limit is 100 requests per 60 s per key, with the headers `X-RateLimit-Limit`,
  `-Remaining` and `-Reset` (Pixabay API docs, read today without a key).

**Request 2, the file, sent as soon as the lookup answers:**
- Without full access, `pixabayFiles` returns only `largeImageURL` (`lib.ts:265`). That is a
  `https://pixabay.com/get/<token>_1280.jpg` link tied to our key.
- `download()` (`handler.ts:110`) follows up to 3 redirects by hand, only to `pixabay.com` or `cdn.pixabay.com`.
  Each hop is one more request. All hops share one 20 s timeout.

**What that adds up to:**
- One pick = 1 API request + 1 file request (+ redirect hops).
- **There is no duplicate request.** The panel blocks a second pick while one runs (`js/cover/stock.js:238`,
  `S.busy`), and `functions.invoke` does not retry.
- The 429 came on request 2. The lookup worked, so the API window was not used up.
- **No User-Agent is set.** `getJson` passes `{}` as headers for Pixabay, and `download()` passes none, so Deno's
  default `Deno/<version>` goes out (B4, H3).

### F2 · Why the first pick hits 429 (three possible reasons; Part 0 decides, B4)
- **H1, our key's `/get/` window.**
  - The browser shows results straight from Pixabay: `webformatURL` thumbnails, 24 a page, and `largeImageURL` in
    the large preview. Those links carry our key's token.
  - Since E16.1, the Pixabay tab searches when it opens and loads more pages on scroll, 3 s apart.
  - If Pixabay limits `/get/` per key, the server's download is the request that gets 429. A window of about 60 s
    fits "65 s worked".
- **H2, a limit per IP.** Edge Functions share outbound addresses with other projects.
- **H3, a bot filter.** Pixabay may reject the default `Deno/x` User-Agent, or treat the shared outbound address
  as a bot.

## Design

### Item 1 · Pixabay: fix the cause first, retry as the fallback (stock v2; B4)
**Part 0 picks the cause and reports the options at STOP 0:**
- **If H1 holds** (many `/get/` loads on our key before each pick):
  - a) the large preview reuses the thumbnail that is already loaded (`webformatURL`, from the browser cache, so no
    new request), with `largeImageURL` only on a click to zoom; or
  - b) the tiles use `previewURL` (`cdn.pixabay.com`, not tied to our key; 150 px, so softer on a 2× screen); or
  - c) the tiles load lazily (`loading="lazy"`), so only tiles on screen are fetched.

  My first choice is a) + c): no visual change, and fewer key-bound requests.
- **If H3 holds:** the stock function sends a clear `User-Agent: NicheInk-stock/2 (+https://nicheink.com)` (no
  personal data) and `Accept: image/jpeg, image/png` on Pixabay requests.
- **If neither holds (H2 alone):** the retry and countdown below are the only fix.

**The server retry (a fallback in every case):** one helper, `withRetry`, in `handler.ts`.
- It is used for the Pixabay **lookup** and **download** only, not for searches or Unsplash (Q-8). Each attempt
  gets its own timeout signal.
- **Retried:** HTTP 429, 502, 503 and 504, and a network error (TypeError).
- **Not retried:** a timeout, and any other 4xx.

**Reading the wait (pure functions in `lib.ts`, unit-tested):**
- `retryAfterSeconds(headers, now)` reads, in this order:
  1. `Retry-After` as seconds (`"12"`);
  2. `Retry-After` as an HTTP-date (`Date.parse` minus the function's clock, never below 0);
  3. `X-RateLimit-Reset`, in seconds.

  Anything else gives null.
- `backoffMs(rand)`: 1.5 s plus full jitter up to 1 s, for when no header comes.

**The wait budget (B4).** A window of about 60 s means a 15 s wait rarely helps, so I propose:
- **at most 1 retry, and at most 5 s of waiting**, with a **30 s deadline** for the whole pick (each attempt's
  timeout is cut to the time left);
- header ≤ 5 s: wait for it, then retry once;
- header > 5 s: no wait. Return 503 `{ error: "stock_busy", retry_after_s: N }`, with N = ceil(header), capped at
  120;
- no header: 1 quick retry after `backoffMs`. If that fails, `stock_busy` with `retry_after_s: 65` (Q-9; Part 4
  replaces 65 with the header numbers seen live);
- a 503, 502, 504 or network error: 1 quick retry, then today's codes.

STOP 0 confirms this or goes back to 2 retries and 15 s if the live logs show short windows.

**The log line (numbers only, never a URL):**
`stock: pixabay download HTTP 429 (try 1 of 2, wait 0 s, retry-after 41, reset 41, remaining 0)`.

**Edge Function limits (Part 0 confirms from the Supabase docs, read only):**
- Free plan: 150 s wall clock, 150 s request idle timeout, 2 s of CPU (waiting does not use CPU).
- `functions.invoke` sets no timeout of its own.
- Our worst case is 30 s.

**The 09 panel (owner Q-1: a planned difference to design 63):**
- A pick answers `stock_busy` with `retry_after_s` ≤ 120: the error slot shows
  "Pixabay is busy. Trying again in N s.". It counts down, is announced once (`role="status"`), then the panel
  retries the same pick once on its own.
- If that retry fails too, the panel shows design 63's message.
- Picking another picture, closing the picker or leaving 09 cancels the wait.
- With stock v1 (no `retry_after_s`), the panel shows today's message. **The front end works with stock v1**
  (needed by B3).
- Compare shot next to `design/screens/63-09-cover-images-pixabay.png`.

**A failed upstream call does not use up the user's limit:**
- Retries inside one request share one reservation.
- After a `stock_busy`, a `stock_unavailable`, or a `server_error` that comes after the reservation, the function
  calls `stock_release(id)` (item 2).
- The panel's automatic retry is a new request with its own slot.

**Kept as is:**
- user JWT only, no service role;
- the host allowlist on every hop;
- pick by id, and the cache re-check;
- the download into our bucket, and the credit;
- the 10 MB and 12,000 px caps;
- no URL or key in the logs.

### Item 2 · Atomic reserve (migration 0032; B1)
**`public.stock_reserve(p_source text, p_action text, p_provider_calls smallint) returns jsonb`.**
It is `security definer`, `set search_path = ''`, with every name schema-qualified, and volatile. It has **no
budget input.** The limits are constants inside the SQL:

| Limit | Value |
|---|---|
| searches per user per minute | 30 |
| picks per user per minute | 10 |
| Unsplash calls per hour, all users together | **45** (shared budget) |
| Unsplash calls per hour, per user | **30** (B1; proposed) |

**Why 30 per user:** one user calling the RPC directly can use at most 2/3 of the shared budget, so 15 calls an
hour stay for everyone else. With Unsplash on Search only (N10), 30 is 10 searches + 10 picks an hour. That is
today's limit for the owner minus 15, which is enough for one cover session. The owner can say another number at
STOP 1.

**Steps:**
1. `uid := auth.uid()`; null → raise 42501. Check the inputs: the source, the action, and 0 to 2 calls (1 for a
   Pixabay pick, 2 for an Unsplash pick).
2. `pg_advisory_xact_lock(hashtextextended('nicheink.stock.user:' || uid, 0))`. One lock per user, because the
   minute limits cover both sources, as today.
3. Unsplash with calls > 0: also `pg_advisory_xact_lock(hashtextextended('nicheink.stock.unsplash', 0))`. The user
   lock always comes first, so there is no deadlock.
4. Count the user's searches and picks in the last minute, released rows excluded. At 30 or 10 →
   `{ ok: false, code: 'rate_limited' }`.
5. Unsplash:
   - the user's own `sum(provider_calls)` in the last hour + this call > 30 → `{ ok: false, code: 'stock_busy' }`;
   - the sum over **all users** in the last hour + this call > 45 → `{ ok: false, code: 'stock_busy' }`.

   Released rows count in both sums, because Unsplash was really called.
6. Insert the row with `user_id = uid` → `{ ok: true, id }`. The locks end with the transaction, after the insert.

**`public.stock_release(p_id bigint) returns boolean`** (definer, `search_path = ''`). It sets `released_at = now()`
only when all of these hold:
- the row is the caller's own;
- it is not released yet;
- it is younger than 2 minutes;
- the caller has fewer than 5 releases in the last hour.

So a user who calls it by hand frees at most 5 minute-slots an hour, and never frees Unsplash budget (Q-5).

**Table changes (additive; v1 keeps working):**
- `stock_calls.released_at timestamptz null`. `stock_calls_guard` also sets `new.released_at := null` on insert, so
  no one can insert a released row by hand. v1 never writes this column.
- Partial index `stock_calls_unsplash_at_idx on stock_calls (at) where source = 'unsplash'`.
- Unchanged for stock v1:
  - `stock_usage()`;
  - the direct insert policy on `stock_calls`;
  - RLS on `stock_calls` and `stock_cache`.

  There is still no update or delete grant to authenticated.
- Grants: `revoke execute … from public, anon` and `grant execute … to authenticated`, for both new functions.

**stock v2 flow:**
- Parse the input, then read the key.
- Search: read the cache first, then `reserve(search, hit ? 0 : 1)`.
- Pick: `reserve(pick, 1 or 2)`, then call the provider.
- If the reserve call fails, stop before any provider call (fail closed, as today).
- `STOCK_UNSPLASH_HOURLY` and `unsplashBudget` are no longer used (the `index.ts` header says so). A new budget
  needs a migration.

**Open item (B2), listed here and in the STOP 2 report:**
- After stock v2 is live and checked, remove the direct insert policy on `stock_calls` and drop `stock_usage()`.
- That goes in 0033 with E13.3, or in its own small migration, on the owner's word.
- Until then, a user can still insert their own rows by hand. That only fills up their own limits, and the
  per-user cap stops one user from using up the shared budget. (Corrected at STOP 2b: this needed 0032's
  insert guard to apply the cap to direct inserts too, fix A. Before that, a direct insert skipped the cap.)

**Out of scope, listed only:** generate's own non-atomic limit check (open item o6, v3).
