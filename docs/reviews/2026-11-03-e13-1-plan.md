## Answers to the open questions

### Q1. Can typst.ts 0.7.0 run in a Web Worker?
Very likely yes. Proof in the first step of Part 2 before anything else is built.
- Static read of `main.bundle.js`: every `window` use is behind `typeof window < "u"`
  (lines 1548, 3433, 4615), in the renderer classes, or in `preloadSystemFonts`
  (`queryLocalFonts`), which we never call. All 11 `document.` uses are in renderer
  classes (lines 186 to 554). The compiler code starts at line 1249 and uses only
  `fetch`, `WebAssembly` and `performance`, which a worker has.
- A module worker can `import()` a blob URL, so the SRI path from the proof works
  inside the worker. Module workers: Chrome 80+, Safari 15+, Firefox 114+.
- Expected gain: the main-thread freeze goes from 190 ms (publish book) and
  1,934 ms (406 pages) to under 50 ms. The PDF comes back as a transferred
  ArrayBuffer (247 KB to 2.34 MB in the proof), no copy.
- Pass rule for the spike: the test book compiles in a worker in Chrome and Safari,
  page count and bytes equal the main-thread build, longest main-thread task during
  the compile under 50 ms.
- Fallback if it fails: compile on the main thread as in the proof. The
  "Making your PDF" state is painted first (two animation frames before the
  compile), the preview rebuilds only 800 ms after the last change, and the worker
  question goes to E13.2. Cost: 190 ms freeze for the real book, about 2 s for a
  400-page book.
- Memory: the worker holds the +263 to +457 MB. 08 ends the worker when the writer
  leaves the step, so the memory goes back.

### Q3. How is "changed since export" detected?
One SQL function, `public.format_key(book_id) → text`, is the only rule. It is the
md5 of one jsonb with every input that changes the PDF:
- format settings: style, parts (on/off), contents shows sections, chapter label,
  drop cap, chapters start on a right-hand page, running header, header title, ISBN;
- Also by: the ticked books that are still valid (same user, same pen name), in
  order, with their title and subtitle;
- the book: title, subtitle, pen name, trim (from the Brief);
- the md5 of the pen name bio, only when About the author is on;
- the version list: today's current version ids of the sections that go in the
  PDF (status Final, text not blank, kind chapter, or intro or conclusion when that
  part is on), in chapter and section order. Same rule as 0025 with include "final".
Not in the key: paper (it does not change the interior PDF; 09 Cover reads it for
the spine), the copyright year, the template version.
How it is used:
1. 08 reads the key with its data (`format_json`). The worker builds from that data.
2. The export row sends `settings_key` = the key it built from. The guard computes
   `format_key` again and refuses a mismatch (P0001 `export_stale`: "Your book
   changed while the PDF was made. Make it again."). So the stored key is always
   the database's key, never a browser guess.
3. "Changed" = `format_key(book) is distinct from` the last PDF row's `settings_key`.

### Q4. Where do the fonts live?
On jsdelivr, from the npm packages in the Q2 table, pinned to exact versions.
Each file has a sha384 SRI hash, made in Part 2 with `openssl` from the CDN file
and checked against the npm tarball (as E13.0 did for Source Serif 4). All five
packages ship `LICENSE_FONT` (OFL 1.1).
Second CDN: unpkg.com, same npm bytes, so the same SRI hash. Every file (engine JS,
wasm, fonts, pdf.js): jsdelivr, one retry after 1 s, then unpkg. A file that fails
its hash is never used. Part 2 checks every hash on both CDNs.
Progress bar: `fetch(…, { integrity })` gives no body until the whole file is
checked. So we stream without `integrity`, count bytes, then check sha384 with
`crypto.subtle.digest` against the same hash. Same safety, with progress.
Not now: self-hosting on GitHub Pages (a 28 MB wasm in a public repo history).
Kept as the next fallback if two CDNs prove weak.

### Q5. How do the stepper "08 done" and the Books card read the export?
One new SQL function, `public.pdf_marks(p_book_id uuid default null)`: for each of
the caller's books (or one book), the last PDF export: `exported_at`, `page_count`,
`changed` (Q3 rule). Under the caller's RLS.
- Stepper (`js/book.js`): reads `pdf_marks(book)` with the book, again after an
  export and when 08 opens. 08 is done when a PDF exists and `changed` is false
  (check mark). When changed, no check, and the reason line says
  "Changed since your last PDF. Export again."
- Books card (`app/dashboard.html`): calls `pdf_marks()` next to `export_badges()`,
  in parallel, one call each. Shows "Print PDF · 48 pages" (success) or
  "Changed since export" (neutral). Next to or in place of the DOCX mark: per artboard.
  A failed read shows no mark and no error, as today.
`export_badges()` stays unchanged (DOCX only).
