## 4. P5: the 100,000 cut never splits a word or a marker

- **Rule (the same in both places):** if the text is at most 100,000 characters, nothing changes. Otherwise:
  1. Cut at 100,000.
  2. If the cut falls inside a word, go back to the last whitespace (` \t\n\r\f\v`, the `md_word_count` set). With no whitespace at all, keep the hard cut.
  3. If a `[Verify: no source]` spans the cut, go back to its start.
  4. Trim trailing whitespace.
  The space before a marker is a word gap, so step 3 runs after step 2.
- **Files:** `lib/section_write.ts`: `capText` uses the new `cutText(t, max)`. `supabase/migrations/0023_g3_fixes.sql`: a new `public.write_cut(text, int)` (immutable, `search_path = ''`, execute revoked from public, anon and authenticated, granted to service_role, like `write_join`). It replaces `section_run_finish` and `section_run_recover` with the same body, except `left(…, 100000)` becomes `write_cut(…, 100000)`. Same signatures, SECURITY INVOKER, `search_path = ''`, and the revoke/grant lines are restated. `section_run_beat` is not replaced: its `left()` keeps a raw crash copy, and `recover` cuts it again when it saves.
- **0023 holds only:** `write_cut` (new), `section_run_finish`, `section_run_recover` (P5), `section_finding_ok` (P4). The header carries a "Checked before writing" line that the owner fills in.
- **Prompt:** no.
- **Tests (gap 6):**
  - `lib.section_write.test.ts`: `cutText` with a cut inside a word, inside a marker, exactly at a space, no whitespace, and under the cap.
  - `t0023.sql`: `write_cut` on the same cases with the same expected strings, so the two places match. `section_run_finish` with joined text whose cut lands inside a marker: no `[Verify` fragment, at most 100,000, `capped` true. ## 5. P6: Generate stops hitting max_tokens

- **Maths:** measured 1.37 output tokens a word (E10.2). Today `max_tokens = min(3,400, ceil(aim × 1.6) + 200)`. A 2,000-word aim that runs 25% long is 2,500 words × 1.37 = 3,425 tokens, over 3,400. That matches 2 of 26 runs ending at max_tokens.
- **Proposal:** `max_tokens = min(4,200, ceil(aim × 2.0) + 200)`. The factor 2.0 = 1.25 (25% over) × 1.6 tokens a word (1.37 measured, plus room for Markdown, markers and run-to-run variation). The cap is 2,000 × 2.0 + 200 = 4,200. `WRITE.wordsPerCall` stays 2,000. The aim wording stays: no prompt change.

| Aim | Old max_tokens | New | Words that fit at 1.37 t/w (new) |
|---|---|---|---|
| 50 | 280 | 300 | 73 |
| 300 (Write more) | 680 | 800 | 438 |
| 450 | 920 | 1,100 | 657 |
| 500 (no target) | 1,000 | 1,200 | 730 |
| 2,000 | 3,400 | 4,200 | 2,920 (+46%); 2,500 words still fit at 1.6 t/w |

- **Worst-case cost per run** (Sonnet 5.5, $2 in / $10 out per million, confirmed): input up to about 8,300 tokens (large Research 6,800 + 1,500 of the section's own text) = $0.017. Output at the cap: 4,200 = $0.042. **Worst ≈ $0.059**, against ≈ $0.051 today. A run that ends normally costs what it writes, so typical runs do not change.
- **Time:** 4,200 tokens at about 60 tokens a second is about 70 s, under the 100 s soft deadline. A slow run ends "timeout" (partial, not counted) instead of "max_tokens".
- **Files:** `lib/limits.ts` (`MAX_TOKENS.section_write` 3,400 → 4,200, comment), `lib/section_write.ts` (`writeAim` factor and comment). The browser holds no copy of these numbers.
- **Reserve:** the reserve for a 2,000-word call grows by 800 tokens.
- **Migration:** no. **Prompt text:** no. Only `max_tokens` in the request changes.
- **Tests (changed, same count):** `lib.section_write.test.ts:23-33` (the `writeAim` values above, `MAX_TOKENS` 4,200) and `:93` (920 → 1,100), `:210-211` (the reserve sum uses 4,200), `handler.section_write.test.ts:59` (920 → 1,100), `tests/limits-parity.test.js:195` (× 1.6 → × 2.0).
- **Snapshot re-record:** `writeRequest section_write`, `max_tokens: 920` → `1100`, one line. The prompt text does not change. The diff will be shown at STOP 2.

## 8. P9: Improve checks that the selection is in the section

- **Server (`lib/stages.ts` `sectionImprove.check`, a new pure `selectionInText` in `lib/section_improve.ts`):** this check comes after the word limits and before the call. In `ctx.draft` or `ctx.current.content`, there must be one place where `selection` occurs, the trimmed text before it ends with `before`, and the trimmed text after it starts with `after`. The browser builds `before` and `after` trimmed (`js/sentences.js` `tail` and `head`), so "touch" means touching once whitespace is ignored. If no such place exists, the server refuses with the new code `selection_not_in_text` (409, no AI call, no usage row).

Otherwise typing from the last 800 ms is not in the draft yet and the server would refuse a real request. If nothing is unsaved, nothing extra is sent.
